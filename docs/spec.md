# 产品 Spec: 留言墙 Demo

> Spec 用来说明要解决什么问题、为什么要做、做到什么程度。
> 只写对产品行为、用户体验或系统契约有约束的信息；实现细节放到 Design。

---

# 1. 背景与目标

## 1.1 背景

`zsrdut/FeedbackWall` 目前是空仓库（仅一个占位 README），没有任何脚手架、页面或服务。本次需求是该仓库的第一个可运行产品：一个最小的留言墙，用于演示「需求 → 设计 → 编码 → 部署」端到端交付链路。

用户在网页上输入昵称和留言并提交，页面展示全部留言（昵称、内容、创建时间，最新在前）。留言由服务端持久化并通过指定接口读写，因此交付物不是纯静态页，而是一个同时提供页面与 `/api/messages` 的应用服务。

受众为演示场景（内部评审、流程演示），不涉及真实业务流量、登录体系与内容审核。

## 1.2 目标

| 目标 | 衡量方式 | 目标值 / 判断标准 |
|------|----------|-------------------|
| 用户能提交留言并立刻看到结果 | 端到端手工用例 + 接口用例 | 提交成功后列表首位出现该条留言，无需手动刷新页面 |
| 打开首页即可看到全部历史留言 | 接口用例 + 页面用例 | 每条展示昵称、内容、创建时间；最新留言在最上面 |
| 基础校验真实生效（前后端一致） | 边界用例 | 空昵称、空内容、超过 200 字被拦截；刚好 200 字通过 |
| 演示环境可独立启动与验证 | 部署节点冒烟 | 单进程启动后 `GET /api/health`、`GET /api/messages` 返回 200 |
| 重启服务后留言不丢失 | 重启验证 | 重启进程后再次查询，历史留言仍在 |

## 1.3 不做什么

- 不做注册/登录、用户身份与权限控制（昵称仅为展示字段，不做唯一性校验）。
- 不做留言的编辑、删除、回复、点赞、举报与内容审核。
- 不做分页、搜索、筛选、排序切换；列表一次性返回全部留言。
- 不做图片/文件/表情包上传，仅纯文本。
- 不做多实例共享存储、消息队列、缓存等分布式能力（单实例文件存储即可）。
- 不做防刷限流、敏感词过滤、CSRF Token（演示定位，风险见 5.2）。
- 不做多语言、暗色主题、深度响应式适配与浏览器兼容降级。

# 2. 用户与场景

| 用户 / 角色 | 使用场景 | 当前痛点 | 期望结果 |
|-------------|----------|----------|----------|
| 演示者 / 访客 | 打开首页浏览已有留言 | 仓库无任何页面，无法展示能力 | 一屏看到全部留言，最新在最上，信息完整 |
| 演示者 / 访客 | 输入昵称与留言并提交 | 无提交入口 | 提交后立即看到自己的留言出现在列表顶部 |
| 评审人 | 验收提交与校验行为 | 无明确验收口径 | 按本 Spec 的验收标准逐条验证 |
| 部署 / 运维（内部） | 启动与冒烟验证 | 无运行说明与健康检查 | 一条命令启动，健康检查可用 |

**主用户路径**：打开首页 → 看到留言列表（或空态）→ 填写昵称与内容 → 点击「提交留言」→ 按钮进入 loading → 成功后表单清空、列表顶部出现新留言 → 可继续提交。

**异常路径**：填写不合法 → 就地提示且不发请求；请求失败 → 保留已输入内容、提示失败原因、按钮恢复可点。

# 3. 功能需求

## REQ-001: 首页展示留言列表

- **优先级**：P0
- **用户价值**：访客无需操作即可了解当前所有留言。
- **需求描述**：首页加载时请求 `GET /api/messages`，按「最新在前」渲染列表；每条展示昵称、留言内容、创建时间。
- **验收标准**：
  - [ ] 当首页加载完成时，系统应展示接口返回的全部留言，且顺序为最新留言在最上面。
  - [ ] 每条留言应同时展示昵称、内容与创建时间，三者均不为空。
  - [ ] 当接口返回空列表时，系统应展示空态文案「还没有留言，来写下第一条吧～」，而不是空白区域。
  - [ ] 当接口请求失败时，系统应展示错误提示与「重试」按钮，点击重试重新拉取。
  - [ ] 创建时间按浏览器本地时区展示，格式为 `YYYY-MM-DD HH:mm`。
  - [ ] 用户可以清楚感知列表的加载中 / 成功 / 空态 / 失败状态。

## REQ-002: 用户提交留言

- **优先级**：P0
- **用户价值**：访客可以把自己的留言发布到墙上。
- **需求描述**：首页提供表单（昵称输入框、留言多行输入框、「提交留言」按钮）。点击提交后调用 `POST /api/messages`，成功后自动刷新列表（无需手动刷新页面）。
- **验收标准**：
  - [ ] 当用户填写合法昵称与内容并点击「提交留言」时，系统应调用 `POST /api/messages` 并在成功后自动刷新列表。
  - [ ] 提交成功后，新留言应出现在列表最上方，表单中的昵称与内容应被清空。
  - [ ] 提交成功后应给出可感知的成功反馈（如顶部提示条）。
  - [ ] 当提交请求进行中时，按钮应展示 loading 状态（禁用 + 文案「提交中…」），且重复点击不会产生第二条留言。
  - [ ] 当提交失败时，系统应保留用户已输入内容、展示失败原因，并恢复按钮可点击。
  - [ ] 用户按 Enter 在昵称输入框提交时，行为与点击按钮一致；留言输入框内 Enter 用于换行。

## REQ-003: 基础校验

- **优先级**：P0
- **用户价值**：避免产生空留言与超长脏数据，保证列表可读。
- **需求描述**：昵称与留言内容在提交前做客户端校验，服务端做同等校验并作为最终判定。
- **验收标准**：
  - [ ] 昵称去除首尾空白后为空时，系统应阻止提交并提示「请输入昵称」。
  - [ ] 留言内容去除首尾空白后为空时，系统应阻止提交并提示「请输入留言内容」。
  - [ ] 留言内容按 Unicode 码点计数超过 200 时，系统应阻止提交并提示「留言内容最多 200 字」；刚好 200 字应允许提交。
  - [ ] 昵称去除首尾空白后超过 30 字时，系统应阻止提交并提示「昵称最多 30 字」。
  - [ ] 当客户端校验被绕过（如直接调用接口）时，服务端应返回 400 且不写入任何数据。
  - [ ] 校验失败时，用户已输入的内容不应被清空。

## REQ-004: 后端 API

- **优先级**：P0
- **用户价值**：为页面提供稳定的数据读写契约，并可被独立验证。
- **需求描述**：提供 `GET /api/messages`（获取列表）与 `POST /api/messages`（新增留言），请求/响应均为 JSON。
- **验收标准**：
  - [ ] `GET /api/messages` 应返回 200 与全部留言，按最新在前排序，字段包含 `id`、`nickname`、`content`、`createdAt`。
  - [ ] `POST /api/messages` 收到合法数据时应写入一条留言并返回 201 与新建留言对象；`createdAt` 由服务端生成（ISO 8601 UTC）。
  - [ ] `POST /api/messages` 收到非法数据时应返回 400 与稳定的错误码，且列表条数不变。
  - [ ] 未知路径应返回 404；非 GET/POST 方法访问 `/api/messages` 应返回 405。
  - [ ] 服务端内部错误时应返回 500 与 JSON 错误体，不泄露堆栈与文件路径。

# 4. 产品规则

## 4.1 页面与交互

| 位置 / 入口 | 用户操作 | 系统反馈 | 备注 |
|-------------|----------|----------|------|
| 首页 `/`（顶部） | 打开页面 | 展示标题「留言墙」与一句说明 | 单页，无需登录 |
| 提交区（列表上方） | 输入昵称、内容 | 实时展示内容字数 `n/200` | 昵称必填标识 `*` |
| 「提交留言」按钮 | 点击 / 昵称框内 Enter | 立即进入 loading（禁用 + 「提交中…」），成功/失败后恢复 | 防重复提交 |
| 提交成功提示 | 自动 | 顶部绿色提示「留言成功」，约 2 秒后自动消失 | 可用 `aria-live="polite"` |
| 提交失败提示 | 自动 | 表单下方红色提示具体原因（含服务端错误信息） | 保留输入 |
| 留言列表 | 页面加载 / 提交成功 | 按最新在前渲染卡片：昵称、时间、内容 | 内容保留换行 |
| 空列表 | 无数据 | 展示「还没有留言，来写下第一条吧～」 | 不隐藏提交区 |
| 列表加载失败 | 请求失败 | 展示「留言加载失败，请重试」+「重试」按钮 | 提交区仍可用 |

## 4.2 字段与校验

| 字段 | 类型 | 是否必填 | 默认值 | 校验规则 | 展示 / 使用位置 |
|------|------|----------|--------|----------|-----------------|
| nickname | 单行文本 | 是 | 无 | 去首尾空白后 1–30 字（按 Unicode 码点计） | 表单输入、留言卡片 |
| content | 多行文本 | 是 | 无 | 去首尾空白后 1–200 字（按 Unicode 码点计） | 留言表单、留言卡片（`white-space: pre-wrap`） |
| id | 字符串 | 系统生成 | 无 | UUID v4，全局唯一 | 列表项 key |
| createdAt | 字符串 | 系统生成 | 无 | ISO 8601 UTC（`new Date().toISOString()`） | 列表展示（本地时区格式化） |

规则说明：
- 计数口径统一为 Unicode 码点（`Array.from(str).length`），不使用 `maxlength` 属性，避免 emoji 计数不一致。
- 服务端对 `nickname`、`content` 均先 `trim()` 再校验与存储，存储 trim 后的值。
- 昵称不要求唯一，允许重名。

## 4.3 状态与流转

| 操作 | 前置状态 | 目标状态 | 用户可见反馈 |
|------|----------|----------|--------------|
| 页面打开 | 列表未加载 | 列表加载中 | 列表区骨架/「加载中…」 |
| 列表请求成功且有数据 | 列表加载中 | 列表有数据 | 留言卡片，最新在最上 |
| 列表请求成功但为空 | 列表加载中 | 空态 | 空态文案 |
| 列表请求失败 | 列表加载中 | 列表错误 | 错误提示 + 重试按钮 |
| 点击提交（校验通过） | 提交空闲 | 提交中 | 按钮禁用 + 「提交中…」 |
| 提交成功 | 提交中 | 提交空闲 | 成功提示、表单清空、列表刷新 |
| 提交失败 | 提交中 | 提交空闲 | 错误提示、输入保留、按钮恢复 |
| 校验不通过 | 提交空闲 | 提交空闲 | 字段级错误提示，不发请求 |

## 4.4 接口或数据契约

| 契约对象 | 变化内容 | 是否兼容 | 关联需求 |
|----------|----------|----------|----------|
| `GET /api/messages` | 新增：返回 `{ "messages": Message[] }`，200，最新在前 | 是（新增接口，无历史调用方） | REQ-001、REQ-004 |
| `POST /api/messages` | 新增：请求 `{ nickname, content }`；成功 201 `{ "message": Message }` | 是（新增接口） | REQ-002、REQ-004 |
| 错误响应 | 新增：`{ "error": { "code": string, "message": string } }`，400/404/405/413/500 | 是（新增接口） | REQ-003、REQ-004 |
| `GET /api/health` | 新增：`{ "status": "ok" }`，用于部署冒烟 | 是（新增接口） | 部署验证（非用户功能） |

`Message` 结构：`{ "id": string, "nickname": string, "content": string, "createdAt": string }`。

错误码：`NICKNAME_REQUIRED`、`NICKNAME_TOO_LONG`、`CONTENT_REQUIRED`、`CONTENT_TOO_LONG`、`INVALID_JSON`、`PAYLOAD_TOO_LARGE`、`NOT_FOUND`、`METHOD_NOT_ALLOWED`、`INTERNAL_ERROR`。

# 5. 约束与风险

## 5.1 非功能要求

| 类别 | 要求 | 验收方法 |
|------|------|----------|
| 性能 | 500 条留言以内，首页加载 + 渲染在本地环境 1 秒内完成；接口响应 P95 < 200ms（单实例、本地文件存储） | 本地压测/手工计时 |
| 安全 | 用户输入仅作为纯文本渲染（禁止 `innerHTML` 拼接），服务端二次校验；错误响应不返回堆栈、绝对路径 | 代码评审 + XSS 字符串用例（`<img src=x onerror=alert(1)>`） |
| 可用性 | 服务重启后历史留言保留；单次写入采用原子替换，避免文件半写损坏 | 重启验证 + 写入中断用例 |
| 兼容 | 支持 Chrome / Edge / Safari 最近两个大版本；移动端窄屏（≥360px）可用 | 手工多浏览器检查 |
| 可观测 | 每个请求输出一行日志（方法、路径、状态码、耗时）；启动日志输出端口与数据文件路径 | 查看进程日志 |
| 可维护 | 零第三方运行时依赖，`npm start` 即可启动；逻辑分层（路由 / 校验 / 存储）可单测 | 代码评审 + `npm test` |

## 5.2 风险与待确认

| 类型 | 描述 | 影响 | 处理方式 |
|------|------|------|----------|
| 风险 | 需求要求后端 API，但目标仓库未启用 GitHub Pages，纯静态托管无法承载 `/api/messages` | 高：部署节点若只有静态托管则无法上线 | Design 采用「单进程 Node 服务同时托管静态页与 API」；部署节点须提供可运行 Node 22 的环境与端口 |
| 风险 | 文件存储 + 单实例：容器无持久卷时重启/重建会丢数据，也不支持多副本 | 中：演示可接受，生产不可用 | 通过 `DATA_DIR` 指向持久卷；风险在 README 与 Design 中标注 |
| 风险 | 无鉴权、无限流、无敏感词过滤，接口可被任意调用 | 中：仅演示环境可接受 | 部署在受控环境；如需公网暴露需另行评估（不在本次范围） |
| 风险 | 昵称 30 字上限为需求未明确、由设计推导的防御规则 | 低：可能与后续产品预期不一致 | 通过 `MAX_NICKNAME_LENGTH` 配置，默认 30；不阻塞本次交付 |
| 待确认 | 无（本次无阻塞性待确认项；部署运行时可行性由部署节点验证） | — | — |
